# 3D タワーディフェンス — v1.0 設計書 (GDD)

> **このドキュメントの使い方**
> これは **v1.0 の固定スコープ**です。ここに書かれていない機能は実装しないこと。
> 「Non-Goals」に挙げたものは v1.0 では作らない。良いアイデアは Backlog に追記するだけにする。
> 実装は「実装順」に従い、**各ステップで常に実行可能（遊べる）状態**を保つこと。

## 1. Project Goal

ソロ開発で、ローポリ/スタイライズドの 3D タワーディフェンスを v1.0 として完成・公開する。
ポートフォリオとして「一つのコアループを技術的にきれいに閉じられること」を示す。

## 2. Problem / Why

- 2D はアート量が多く消耗しやすい。ローポリ 3D はモデル再利用・ライティングで見栄えを稼げる。
- 「見た目の作り込み」ではなく「システム設計・アルゴリズム」で価値を出せるジャンルとしてタワーディフェンスを選択。

## 3. Target User

- **プレイヤー**: ブラウザでサッと遊ぶカジュアル層。ルール説明なしで直感的に遊べること。
- **ポートフォリオの読み手**: 採用担当・レビュアー。規模より「設計の考え方」を見る。

## 4. 作るゲーム（コンセプト）

- 敵が決まったルートを進んで拠点（クリスタル）に到達しようとする。
- プレイヤーは設置可能マスにタワーを置き、自動攻撃で敵を倒す。
- キルでゴールドを得て、次のタワーを買う。ウェーブが進むほど敵が強くなる。
- 全ウェーブを耐えれば勝利、ライフが 0 になれば敗北。
- テーマは仮（例: スライムがクリスタルを狙う）。モデルが単純になるものなら差し替え自由。

## 7. Tech Stack

- **エンジン**: Godot 4.x / GDScript
- **アセット**: Blender（Claude + Blender MCP で叩き台生成）→ glTF (.glb) で書き出し
- **配布**: Godot HTML5 エクスポート → itch.io
- **バージョン管理**: Git / GitHub

## 8. ノード構成（Godot）

```
Main (Node3D)
├─ Level (Node3D)
│   ├─ Path3D                … 敵のルート（Curve3D を編集）
│   ├─ BuildSpots (Node3D)   … 設置可能マス（Area3D or Marker3D を複数）
│   └─ Base                  … 拠点（到達=ライフ減少）
├─ WaveManager (Node)        … 敵スポーン・波の進行
├─ Towers (Node3D)           … 設置したタワーの親
├─ UI (CanvasLayer)          … ゴールド/ライフ/ウェーブ/ボタン/勝敗画面
└─ GameState (Autoload)      … gold, lives, wave とシグナル
```

**主要シーン**

- **Enemy**: `Path3D` の子として `PathFollow3D` を生成し、その下に敵ビジュアル＋ロジック。
  - スクリプトで `progress` を毎フレーム進める。HP・速度・撃破ゴールドを保持。
  - シグナル: `died(gold_value)`, `reached_end(damage)`
- **Tower**: `Node3D` + `Area3D`(射程) + `Timer`(発射間隔) + 砲身メッシュ。
  - ターゲット選択は **「ゴール（進行度）に一番近い敵」** を狙う。
  - 発射で Projectile を生成（またはヒットスキャン）。
- **Projectile**: `Area3D` + メッシュ。ターゲットへ移動し、命中でダメージ。

## 9. データ駆動設計（エンジニアの見せ場）

ステータスをコードにベタ書きせず Godot の `Resource` に分離する。README で語れる設計ポイント。

- `TowerData (Resource)`: cost, damage, range, fire_rate, effect(none/slow)
- `EnemyData (Resource)`: max_hp, speed, gold_value
- `WaveData`: 各波の「敵種 × 数 × 出現間隔」

**GameState (Autoload) のシグナル**

- `gold_changed(new_value)`
- `lives_changed(new_value)`
- `wave_changed(index)`
- `game_over()` / `game_won()`

## 10. 必要アセット（ローポリ / Blender MCP で量産）

- 地面（マップベース）×1 … `scripts/terrain.gd` で手続き生成（高台＋崖＋低地）
- ルートの見た目（メッシュ帯 or デカール）×1 … `scripts/road_visual.gd` で手続き生成
- 拠点クリスタル ×1 … `scripts/base_crystal.gd` で手続き生成（結晶＋台座＋明かり）
- 敵ブロブ（通常）×1 ＋ 高速版（色/サイズ替え）… `scripts/low_poly.gd` の塊メッシュ
- 岩・茂み・木 … `scripts/prop_scatter.gd` で MultiMesh にばら撒き
- タワー（土台＋砲身）… 2 種とも Blender 製モデルに差し替え済み
  - アロータワー: `assets/models/tower_basic_*.glb`（`tower_basic.blend` / `TowerBasic`）
  - フロストタワー: `assets/models/tower_slow_*.glb`（`tower.blend` / `TowerSlow`）
  - 書き出し方:
    `blender -b <blend> --python tools/export_tower_models.py -- assets/models <接頭辞> <出力名>`
  - 土台と砲塔を別 .glb にするのは、Godot 側で砲塔だけを旋回させるため。
    砲身は Blender の +Y に向けて作ると回転補正が入らない（-Y なら書き出し時に 180 度回る）。
  - `scenes/tower.tscn`（プリミティブ表示）は TowerData.tower_scene 未指定時の
    フォールバックとして残してある。
- 弾（球）×1
- 設置可能マスのマーカー（リング/パッド）×1
- フォント: `assets/fonts/NotoSansJP-Regular.otf`（SIL OFL / `OFL.txt` 同梱）
  - Godot 内蔵フォントに日本語グリフが無く、Web にはフォールバック先のシステム
    フォントも無いため、同梱しないと UI が豆腐になる（デスクトップでは気づけない）
  - `project.godot` の `gui/theme/custom_font` で既定フォントに指定している

ベースを 1 個作って **色・スケール違いで増やす**。有機的で難しいモデルは作らない。

### 21 で入れたもの（itch.io のプレイヤーから届いた指摘への対応）

公開後に実際に遊んだ人から届いた 6 件。ロードマップの続き（VFX/BGM・減速タワー）より
実プレイを塞ぐ不具合寄りの指摘だったため、そちらより先に対応した。

1. **「画面が小さい」「全画面が欲しい」** — HUD 左上に ⛶ ボタンを追加
   (`hud.gd._on_fullscreen_pressed`)。`DisplayServer.window_set_mode` は
   Web 書き出しでもブラウザの Fullscreen API を叩いてくれるので、
   デスクトップと同じコードで済んだ。itch.io 側の埋め込み枠が小さい問題は
   コードでは直せないので、埋め込みサイズの見直しは別途プロジェクト設定側で。
2. **「射程が置く前に見えない」** — `BuildGridView` にリング (`TorusMesh`) を追加し、
   タワーを選んでマスにカーソルを乗せた時点で射程を表示する
   (`set_cursor(cell, buildable, attack_range)`)。既存の `-- grid` プレビューにも
   同じ表示が出るようにしてある。
3. **「ボタンを押しているか分かりにくい」** — `resources/ui/theme.tres` を作り、
   プロジェクト既定テーマ (`project.godot` の `gui/theme/custom`) にした。
   pressed 状態だけ地の色をゴールドに変えて、選択中のタワーボタンや
   トグル状態がひと目で分かるようにした。
4. **「説明が無く、ステージが変わってタワーが消えて詰んだ（強化に全額使うパターン多数）」**
   — 2 つで対応。
   - `HelpScreen`（`scripts/help_screen.gd`）: ステージ 1 の開始時に 1 回だけ自動で
     開く遊び方説明。「タワーはステージが変わると全部消える」を明記した。
     **SceneTree は止めない。** WaveManager は「押さなくても待ち時間で進む」設計
     (`auto_start` / `first_wave_delay`) なので、ここで一括ポーズを挟むと
     `headless_check` / `tools/vis_preview.tscn`（どちらも main.tscn をそのまま
     読み込んで動かす）が誰にも閉じられないまま固まって壊れる
     ——実際に一度やって `balance_sim` 系の指標が全部 0 になるところまで確認して直した。
     `?` ボタンからの手動オープンだけ勝敗画面と同じくポーズする。
     自動表示は `OS.get_cmdline_user_args()` が空のときだけ
     （vis_preview は `-- モード名` を付けて main.tscn を読み込むため）。
   - `IntervalScreen` に警告文を追加（`_refresh_warning`）: 今の所持金で
     一番安いタワーすら建たないときだけ「⚠ タワーは次のステージで一新されます」
     と出す。強化を止めはしない（判断はプレイヤーに残す）が、詰みの手前で気づける。
5. **「弓兵や戦士の攻撃が分かりにくい」** — `Warrior._play_attack_vfx()` を追加。
   ダメージ自体は今までどおり `_fight()` で即座に決着するので、これは見た目だけの
   後付け。近接（盾兵・衛兵）は `_visual` を前へ小さく踏み込ませ (`_lunge`)、
   弓兵は矢に見立てた薄い箱を的まで飛ばす (`_spawn_arrow`)。着弾には
   `Burst.Kind.HIT` を追加で出し、タワーの弾と同じ「当たった」表現に揃えた。

検証: `headless_check` ゴールド 748・波 1・減速観測 true（HelpScreen 追加前と同じ数値
——ポーズを挟まない設計になっていることの裏付け）、`balance_sim --campaign` は
変わらず WON（ステージ 3 残りライフ 7）。見た目は `vis_preview -- grid` で射程リングと
ボタンの pressed 色、`-- archer` で弓兵の矢を確認した。

### 22 で入れたもの（続報の 3 件）

1. **「ステージ表記がない」** — HUD の WAVE 表示に `STAGE %d/%d` を足した
   (`hud.gd._on_wave_changed`)。ステージは `wave_changed` と別のタイミングでも
   変わる（`advance_stage()` 直後、波がまだ 0 に戻る前）ので、
   `GameState.stage_changed` も同じハンドラにつないで両方から更新する。
2. **「一時停止が無い」** — `PauseScreen`（`scripts/pause_screen.gd`）を追加。
   HUD の ⏸ ボタンから開き、勝敗画面・インターバル画面と同じ
   「SceneTree.paused で止めて Control を出す」型にした。
   **HelpScreen と違ってこちらは常に手動でしか開かない**ので、
   ポーズを挟んでも headless_check / vis_preview を壊さない
   （HelpScreen のときに踏んだ事故の再発防止として、`-- pause` プレビューモードで
   「開く→ポーズ true」「再開→ポーズ false」まで確認している）。
3. **「無限モードがゴールド無しで始まって詰む」** — 原因は、最終ステージだけ
   `IntervalScreen`（強化を買う場所）を経由せず直接勝利するため。
   1 つ前のインターバルで強化に寄せすぎていると、最終ステージの収入だけを
   持って無限モードへ入ることになり、タワー 0 本の盤面から始まってしまっていた。
   `GameState.start_endless()` で **所持ゴールドを最低でも START_GOLD (1100) まで
   補う**ように直した（`gold = maxi(gold, START_GOLD)`）。通常の周回開始と
   同じ前提に揃えただけなので、無限モード開始直後の難度は変えていない。

検証: `headless_check` は変わらず波 1・ゴールド 748・減速観測 true。
見た目は `vis_preview -- grid` で `STAGE 1/3` 表記と ⏸ ボタン、
`-- pause` で開閉のポーズ切り替えを確認した。

`balance_sim --campaign --endless`（周回全体・約 3800 秒ぶん）は 5 周目のステージ 3
波 8（敵の硬さ ×2.40）で敗北。**`balance_sim` はインターバルで方針どおりに買うだけで
使い切りはしないので、もともと START_GOLD の床には掛からない**——今回のゴールド補填が
効くのは「プレイヤーが強化に寄せすぎて無限モード開始時に手持ちが少ない」ときだけで、
機械的な検証の到達周回数そのものは変わらない設計。実際、何周目まで届くかは
乱数で 1 周ぶんは普通にぶれる（§13 既出の注意どおり）ので、この数値は
「詰みなく最後まで走り切れる」ことの確認として見ている。

### 23 で入れたもの（盾兵だけ Blender モデルに差し替え）

戦士は procedural（`LowPoly.blob` の塊＋装備 1 個）で統一する方針だった
（§16.4-5 前半のコメント、および過去に「装甲ロボ風にフル造形して作り直しになった」
実例——`assets/models/source/warrior_crystal_warden*.blend` として残っている）。
今回はユーザーが `warrior_knight.blend` を新しく作って持ち込んだので、
**盾兵 1 役職だけ**に絞って取り込んだ（ユーザーとの相談で決定。衛兵・弓兵は procedural のまま）。

- `tools/export_warrior_models.py` … タワーと違って部位ごとに旋回させる必要が無いので、
  Base/Turret に分けず 1 つの .glb にまとめて書き出すだけでよい。
  `Kn_` 接頭辞のメッシュ（Ground は除く）をまとめて `assets/models/warriors/warrior_shield.glb` へ。
- `WarriorData.model_scene`（`scripts/data/warrior_data.gd`）… null なら今までどおり procedural。
  盾兵の `.tres` だけこれを設定した。他の役職は触っていない。
- `Warrior._build_model_visual()`（`scripts/warrior.gd`）… モデルを `_visual` に差し込み、
  **全マテリアルを複製して控えておく**。被弾フラッシュ（`_refresh_color`）は procedural 版が
  「共有マテリアル 1 つの色を差し替える」だけだったのに対し、モデルは部位ごとに複数の
  マテリアルを持つので、同じ見せ方をするには全部を回す必要がある。複製しないと
  インポートしたマテリアルが全インスタンスで共有されてしまい、戦士 1 人の被弾で
  同じ役職の全員が一瞬光る事故になる。
- `body_scale = 1.13`（`resources/warriors/warrior_shield.tres`）… モデルの実寸（地面から
  頭頂まで 0.926 m）を、procedural 版の盾兵（body_scale 1.25 のときの見かけの高さ
  ≒ 1.05 m）に合わせるための倍率。他の役職との見た目の大きさを揃えるためだけの数値で、
  ゲーム上の当たり判定・射程には影響しない。

**ハマった点:** 新規の .glb を追加すると `ERROR: Blender path is invalid or not set` で
インポートが失敗し続けた（.import が作られない）。**ヘッドレスでは Blender 連携の
未設定ダイアログを出せないだけ**で、原因は .glb の中身ではなかった
（同じ内容のコピーでも、既存のタワー用 .glb のコピーでも同じエラーが出た）。
`%APPDATA%\Godot\editor_settings-4.6.tres` に
`filesystem/import/blender/blender_path`（Blender 5.0 の実行ファイル）を足したら直った。
このプロジェクト固有の設定ではなく**ユーザーの Godot エディタ全体の設定**なので、
別プロジェクトで新規 .glb を足すときも効く。

検証: `headless_check` に新規エラー無し。`balance_sim --stage 1 --towers 0 --warriors 6`
（盾兵を含めて戦わせ、被弾フラッシュのコードを確実に通す）でも SCRIPT ERROR 無し。
見た目は `vis_preview -- warrior` で盾兵モデルが procedural な衛兵・弓兵と並んで
違和感の無い大きさで立つことを確認した。

### 24 で入れたもの（スマホ最適化・フロストのティア・盾兵モデルの差し替え）

**1. スマホ最適化**

`window/stretch/mode="canvas_items"` に対して `window/stretch/aspect` を
未設定（既定の `keep`）のままにしていたのが原因で、**16:9 以外の画面では
黒帯で埋まって表示がとても小さくなっていた**。実測（`--resolution` は
`--write-movie` と組み合わせると Movie Maker が解像度を上書きしてしまい効かないため、
`--write-movie` を使わずに `get_viewport().get_texture().get_image().save_png()` で
直接キャプチャして確認した）:

| 画面サイズ | `aspect` 変更前 | 変更後 (`expand`) |
| --- | --- | --- |
| 400×860（縦持ちスマホ相当） | 400×225 だけ描画（残り 74% が黒帯） | 400×748（ほぼ全面） |
| 812×375（横持ちスマホ相当） | 黒帯あり | 812×375（全面） |
| 1280×720（デザイン解像度） | 変化なし | 変化なし（同じ） |

`window/stretch/aspect="expand"` の 1 行で直った。`keep` は「デザインの縦横比を
保つために黒帯を足す」のに対し、`expand` は「足りない分だけ見える範囲を広げる」ので、
四隅に固定した HUD（ゴールド表示・ボタン類）はそのままの位置・大きさで残り、
真ん中の 3D 盤面が広く見えるようになるだけで済んだ——**HUD 側のレイアウトは
一切触っていない**。縦持ちのまま遊べる絵になったので、横持ち固定は不要と判断した。

Web 書き出し側はすでに `html/canvas_resize_policy=2`（adaptive、キャンバスをブラウザの
表示領域いっぱいに広げる）になっていたので、これと組み合わせれば実機のブラウザでも
同じ効果が出るはず（要 itch.io での実機確認）。タッチ入力は Godot 既定の
「タッチをマウスとして扱う」機能に乗っているだけで、専用のコードは足していない
——BuildManager のクリック判定・HUD の Button はどちらもマウスイベント前提のままで動く。

**2. フロストタワーのティア 5 段**

モデルが揃った（`tower_frost_2〜5.blend`、`tools/export_tower_models.py` で
`.glb` 化済み）ので、`tools/make_frost_tiers.py`（`make_tower_tiers.py` のフロスト版）
で鎖をつないだ。既存の仕組み（`TowerData.next_tier` / `upgrade_cost`、
`GameState.current_tower()`）がそのまま使えたので、**シーン側は何も変えていない**
——`main.tscn` の `tower_options` は元から `tower_frost.tres`（鎖の 1 段目）を
指しており、`IntervalScreen._build_rows()` は `next_tier != null` の種類を
自動で行に出す設計だったので、鎖を足しただけで強化 UI に出てきた。

| 段 | 名前 | 設置 | ダメージ | 射程 | 減速 | 強化費用 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | フロストタワー | 170 | 4 | 6.0 | ×0.35 / 2.5s | 500 |
| 2 | グレイシャータワー | 215 | 6 | 6.5 | ×0.30 / 2.8s | 850 |
| 3 | ブリザードタワー | 265 | 9 | 7.0 | ×0.26 / 3.1s | 1100 |
| 4 | パーマフロストタワー | 320 | 13 | 7.5 | ×0.22 / 3.4s | 1450 |
| 5 | アブソリュートゼロタワー | 385 | 18 | 8.0 | ×0.18 / 3.8s | — |

ダメージだけでなく **足止めそのものも段で強くなる**（slow_factor が下がる＝
速度倍率が下がる、slow_duration が伸びる）。`make_frost_tiers.py` の検算は
アロー版の項目（費用・ダメージ・射程の単調増加、鎖が 5 段で終わる、モデル実在）に
「slow_factor が段ごとに下がっているか」「slow_duration が伸びているか」を足した
——足止めが弱くなる段があってはフロストを上げる意味が無いため。

`tools/balance_sim.gd` に `--frost-tier`（`--tier` のフロスト版。費用を払わず
段の火力だけを測る）を追加し、`_try_build_one()` が素の `tower_frost.tres` を
直接読んでいた**既存のバグ**（フロストを強化しても検証ツールには反映されなかった）
も直した。フロスト縛り（`--frost-every 1`）でタワー 3 本の到達ウェーブ:

| 段 | 到達ウェーブ |
| --- | --- |
| 1 | 波 6 で敗北 |
| 2 | 波 7 で敗北 |
| 3 | 波 8 で敗北 |
| 4 | ステージクリア |
| 5 | ステージクリア |

段を上げるごとに着実に伸びる、アローと同じ形の階段になった。

**標準の `--campaign` の強化方針にはフロストを混ぜていない。** 「両方の鎖から
安いほうを買う」を試したところ、フロストの強化費用がアローよりどの段も安いため
毎回フロストが先に選ばれ続け、板の大半を占めるアロー（フロストは
`--frost-every` で 1/3 だけ）が育たないまま**周回全体がステージ 2 で敗北**する
ところまで悪化した（実測）。フロストの強化はプレイヤーが手動で選べる
（インターバル画面に出る）が、この自動検証の既定方針は**アロー優先のまま**にしてある
——フロストだけを測りたいときは `--frost-tier` を使うこと。

回帰: `headless_check` は変わらず波 1・ゴールド 748・減速観測 true。
`balance_sim --campaign`（標準・アロー優先）は 3 回とも WON。ステージ 3 の
残りライフは 3 / 9 / 4 と、以前の基準 (8〜14) よりやや低めだが、`--campaign` は
毎回コースを引き直すため乱数のぶれの範囲内と見ている（負けてはいない）。

7 メッシュ・10 マテリアル・画像テクスチャ無し・アニメーション無し

**剣を振る演出を新しく足した。** これまでの近接（procedural な盾兵・衛兵）は

26 の時点では盾兵・衛兵のモデルがどちらも同じ「blue steel」系パレットで、
役職の見分けをシルエット（大盾の有無）だけに頼っていた。ユーザーから
「見分けがしやすいように配色し、弓兵も作成した」との指示で 3 体の配色と
弓兵のモデルが届いたので、それを反映した。

**役職カラー**（3 体で共通のパレットのうち、胴布・房・帯だけを役職ごとに変える）:

| 役職 | 色 | 頭部のシルエット |
| --- | --- | --- |
| 盾兵 | 生成り（ivory） | 尖頂兜＋房 |
| 衛兵 | 水色（pale blue） | 前後に伸びる鶏冠 |
| 弓兵 | 深緑（forest） | つば広のケトルハット（縁だけ緑の帯） |

色だけでなく**頭部のシルエットも役職ごとに変えてある**。届いた `README.md` によると、

へ上書き）。

### 28 で入れたもの（弾と攻撃演出の作り込み）

「弾道や弓矢の細部のこだわりが足りない」「タレットは種類だけでなく**段ごとにも**
少し変えてほしい」「最終段はレールガンに見えるので範囲攻撃でもいい」という指摘への対応。

**1. 弾を種類と段で分けた**

それまでは**どのタワーも同じ金色の球**を撃っていた（フロストタワーまで金色だった）。
`TowerData` に弾の欄を足して、`.tres` だけで見た目が決まるようにした。

| 欄 | 何 |
| --- | --- |
| `shot` | 弾の種類（BOLT 矢弾 / SHELL 砲弾 / ORB 氷の玉 / BEAM 光線） |
| `shot_color` / `shot_scale` | 弾の色と太さ。**段ごとに変える** |
| `splash_radius` / `splash_falloff` | 着弾時に巻き込む半径と、巻き込まれた側に通る割合 |

| 段 | アロー系 | フロスト系 |
| --- | --- | --- |
| 1 | BOLT・淡い黄 ×0.90 | ORB・水色 ×0.90 |
| 2 | SHELL・橙 ×1.05 | ORB ×1.05 |
| 3 | SHELL ×1.25 | ORB ×1.20 |
| 4 | SHELL・赤橙 ×1.50 | ORB ×1.35 |
| 5 | **BEAM**・白金 ×1.60・巻き込み 1.0 m | ORB・ほぼ白 ×1.55 |

段が上がるほど太く・色が濃く（フロストは淡く）なるので、飛んでいる弾を見れば
何段目かが分かる。`make_tower_tiers.py` / `make_frost_tiers.py` の検算に
「太さが段ごとに増えているか」「色が段で重複していないか」「巻き込みは最終段だけか」を足した。

**2. 弾道**: SHELL だけ山なりに飛ぶ。**放物線は解いていない**——的が動くので
撃った時点の解が途中で合わなくなる。進んだ割合を `sin` で 0 → 1 → 0 と持ち上げるだけ
（高さは飛距離に比例。固定値だと近くへ撃ったときだけ不自然に跳ね上がる）。
弾は実際の移動量のほうを向くので、落ち際にちゃんと下を向く。

**3. 最終段のレールガン**: 撃った瞬間に光線（`BeamFx`）を引き、弾のほうは
非表示で飛ばす。**ヒットスキャン（撃った瞬間に当てる）にしては駄目だった。**

> 実測の経緯（全部 `--towers 3 --tier 5` で測った。変更前は**波 8 で敗北・ライフ 0**）:
>
> | 試した形 | 結果 |
> | --- | --- |
> | ヒットスキャン・巻き込み無し | クリア（ライフ 14 残し） |
> | ヒットスキャン・連射 1.8 → 1.0・巻き込み 1.3 m | クリア（ライフ 20 残し） |
> | 弾のまま・弾速 22 → 60・巻き込み 1.5 m | クリア（ライフ 20 残し） |
> | **弾のまま・弾速 22・巻き込み 1.0 m** | **クリア（ライフ 5〜9 残し）** ← 採用 |
>
> 犯人は火力ではなく**無駄弾が出なくなること**だった。弾には飛翔時間があるので、
> 着く前に的が倒れたぶんは捨てられる。即着弾にするとそれが丸ごと無くなり、
> 連射や巻き込みを削っても戻らない（弾速を上げるだけでも同じことが起きる）。
> 見た目を光線にしたいだけなので、**弾としての性質は他の段と揃えたまま**にした。

巻き込みの半径も実測で 2.2 m → 1.0 m まで絞った。道の上では敵が一列に詰まるので、
半径が広いと 1 発で隊列ごと巻き込んでしまう。

**4. 砲身の反動**: 撃つと砲身が後ろへ蹴れて戻る（`Tower._recoil`）。
動かすのは `TurretModel`（砲塔の子）で、**Muzzle は動かさない**——弾の出る位置が
反動でぶれると着弾までの見た目がちらつく。蹴る量は `shot_scale` に比例するので、
段が上がると撃ち方も重くなる。

**5. 矢の作り直し**: 箱 1 個（ただの棒）だったのを、**矢柄・鏃・矢羽根（十字に 2 枚）**
の 3 部品にまとめたメッシュにした。弓兵のモデルには弓を握った拳（`Bow` ノード）が
あるので、**矢はそこから飛ぶ**。あわせて引き手（`Arm.L`）を弾いて弦を放した動きを付けた
（衛兵の剣振りと同じ `_swing_arm()` を角度と時間を変えて使い回している）。
矢も気持ちだけ山なりに飛ばしている。

検証: `headless_check` は変わらず波 1・ゴールド 748・減速観測 true。
`balance_sim --campaign` は WON（ステージ 3 残りライフ 10）、
`--stage 3 --towers 3 --tier 5` は波 5 で敗北（強化だけでは勝てないことの担保）。
見た目は `vis_preview -- tiers wave` で段ごとの弾と山なりの弾道、`-- fx` で光線と
矢のメッシュを確認した（光線と矢は一時的にプレビュー側へ差し込んで撮り、確認後に戻している）。

### バランスの基準（`tools/balance_sim.gd` で検証）

**v2.0 の基準は「周回 1 本を通しで走らせた結果」**。数値を触ったらこれを回して確認する。

| 走らせ方 | 期待結果 |
| --- | --- |
| `--campaign`（標準） | **勝利**。ライフの残りは ステージ1 20 → ステージ2 11 → ステージ3 3〜9

## 15. v1.1 見栄えアップデート（公開後）

v1.0 公開後に「のっぺりして見える」を潰すために入れた見た目だけの変更。
**ゲーム数値（`.tres`）とルートの `Curve3D` は一切触っていない**ので、
§13 のバランス基準はそのまま有効。

**何がのっぺりの原因だったか**

1. 光源が 1 灯・ほぼカメラ正面から当たっていて、影が出ていなかった
2. 地面が 40×40 の板 1 枚で、面がすべて同じ向き＝同じ明るさだった
3. 道が板を並べただけ、クリスタルが 6 角錐 1 本で、形の情報量が無かった
4. カメラが遠く、Blender 製の砲台が小さくしか映っていなかった

**入れたもの**

- **ライティング**: 逆光寄りの暖色キーライト（影あり）＋ 反対側から寒色のフィルライト。
  環境光を落とし、フォグ・グロー・トーンマップ調整を追加（`scenes/main.tscn`）
- **地形** `scripts/terrain.gd`: 遊べる高台・崖・低地を持つ島を手続き生成。
  面ごとの法線（フラットシェーディング）＋頂点カラーで、テクスチャ無しに陰影を作る。
  **道と設置マスの周りは起伏を平らに均す**ので、y=0 前提の配置は壊れない
- **道** `scripts/road_visual.gd`: カーブの断面をつないだリボン。幅を左右別々に揺らし、
  地形の高さに乗せ、中央を明るく端を暗くして踏み固められた土に見せる
- **拠点** `scripts/base_crystal.gd`: 大小 4 本の結晶＋岩の台座＋オムニライト。
  ゆっくり回転・上下させ、止まった画面でも目を引くようにした
- **小物** `scripts/prop_scatter.gd`: 岩・茂み・木・道端の石を MultiMesh でばら撒く。
  道・設置マス・拠点を避ける判定つき。影が落ちることで平面に情報量が出る
- **設置マス**: 半透明の板 → 石の土台（Pad）＋状態を示す縁（Ring）の 2 段構え。
  タワーを建てた後も土台を残して足元を締める
- **敵**: 球 → 面を粗く割った塊（`scripts/low_poly.gd`）。跳ねるつぶれ／伸びを追加
- **カメラ**: 画角を締めたうえで、見下ろし角を少し起こして遠景が画面に入るようにした。
  **建てたタワーをクリックすると寄って見せる**（`scripts/camera_rig.gd`）。
  もう一度クリック / 右クリック / Esc / 何もない所をクリックで引きに戻る
- **遠景** `scripts/terrain.gd`: 高台から離れるほど立ち上がる山を地形に足した。
  稜線ノイズ（ノイズの絶対値を反転したもの）で尖った峰を作り、高さで岩肌 → 雪に変える。
  格子は中心ほど細かく外ほど粗い可変間隔にして、面数を増やさず 150 単位先まで作る

**遠近感の作り方（GL Compatibility の制約）**

Compatibility レンダラは `Environment` の深度フォグ（`fog_mode = DEPTH`）を無視し、
指数フォグしか効かない。指数フォグは手前にも一様に掛かるので、遠景を霞ませるほど
濃くすると遊ぶ高台まで白くなってしまう。そこで **遠景ぶんの空気遠近は地形の頂点カラーに
焼き込み**（`Terrain.haze_*`）、`Environment` のフォグは木や岩に掛かるぶんだけ薄く残している。
高台の上（輪郭からの距離が負）には焼き込まないので、プレイエリアは澄んだまま。

**Non-Goals（このアップデートでもやらない）**

- ❌ ゲーム数値・ルート・ウェーブ構成の変更（バランスは v1.0 のまま）
- ❌ カスタムシェーダー（GL Compatibility / Web で動くことを優先）
- ❌ 画像テクスチャの導入（頂点カラーとライティングだけで作る）
- ❌ 自由に動かせるカメラ（寄る先は「建てたタワー」だけに限る）

**確認方法**

見た目の変更は `tools/vis_preview.tscn` で撮って確かめる。
本編を読み込んでタワーを数本建てた状態を作るだけのハーネスで、
Godot の Movie Maker モードと組み合わせると PNG が落ちる。

```
godot --path . --write-movie <出力先>/f.png --resolution 1280x720 --quit-after 480 res://tools/vis_preview.tscn
```

末尾に付けられる引数:

- `-- focus` … タワーの上へマウスを飛ばして左クリックを流し込む。`focus_on()` を
  直接呼ばずクリックにしているのは、物理レイヤーの設定や BuildManager による
  入力の横取りまで含めて確かめたいため
- `-- wave` … 「次の波へ」を押して、待ち時間を飛ばして波が始まるかを確かめる
- `-- fx` … エフェクト 4 種をタワーの手前に並べて撒き続ける（見た目の調整用）

## 16. 実装ロードマップ（v2.0 に向けて）

### 16.1 v2.0 のゲーム像

v1.0 は「固定ルート・タワーのみ・8 波で終わり」だった。v2.0 は**周回構造と自軍ユニット**を
入れて、バラックス型のタワーディフェンス（Kingdom Rush 系）にする。

- 全ウェーブ終了でステージクリア → インターバル → 次ステージ（周回する）
- ステージ移行でタワー配置はリセットされる
- クリスタルから自軍の「戦士」が出て、敵を迎撃する
- 戦士は役職を 3 種類。武器は強化できる
- タワー・武器の強化はステージ移行の合間（インターバル）で行う

**決めたこと**

| 論点 | 決定 | 効いてくるところ |
| --- | --- | --- |
| 周回の終端 | 有限ステージでエンディング。無限モードは後付け | ウェーブは手書きの `.tres` のままでよい |
| 戦士の出し方 | ゴールドで雇う（タワーと同じ経済） | `BuildManager` と HUD のボタンをそのまま伸ばせる |
| 強化の持ち越し | 1 周回のみ。負けたらリセット | **セーブ機構が要らない** |
| ステージの違い | クリスタルの位置は固定で、**道だけが変わる** | 道と設置マスがステージごとのデータになる |
| 道の形 | 1 本道 → 回り込み → **分岐あり**、と段階的に複雑化 | 道は線ではなく**グラフ**になる |
| 分岐の選択 | 敵は分岐で **A\*** して次の枝を選ぶ | 経路探索の目玉はここに入る |
| タワーの設置 | 固定マスをやめて**グリッド**に置く | 設置の自由度が上がり、A\* の意味も出る |
| 戦士の移動 | 道に沿って進み、敵とぶつかったら足を止める | **経路探索は要らない**。道グラフを辿るだけ |

セーブが要らないこと、戦士が道から外れないことの 2 つで、重い部分がかなり落ちている。
残った重さは「道のグラフ化」に集約されるので、そこに集中できる。

**v1.0 の Non-Goals から意図的に解禁するもの**

- A\* 経路探索 / グリッド設置
- タワーのアップグレード / ティア
- 3 種類目以降のユニット（＝戦士の役職）
- 複数マップ（＝ステージ）

§6 の Non-Goals は「v1.0 のスコープ凍結」としてそのまま残す。ここは v2.0 の新しいスコープ。

### 16.2 道をグラフにする

ステージの絵は「クリスタルの位置は同じで、そこへ至る道だけが変わる」形。
1 本道 → 四角く回り込む → 内側で折り返して分岐が増える、と段階的に複雑になる。

つまり道は **節（分岐点）と辺（区間）のグラフ**になる。今の `Curve3D` 1 本では表せない。

- 節 = 分岐点とスポーン地点とクリスタル
- 辺 = 節と節をつなぐ区間。**辺 1 本ぶんは今までどおり `Curve3D`** にすれば、
  滑らかな移動も道のリボン生成もそのまま使える
- 敵は辺の上を進み、節に着いたら A\* でクリスタルまでの経路を出して次の辺を選ぶ

**A\* が意味を持つには辺のコストが動く必要がある**

クリスタルの位置が固定で辺のコストも固定なら、A\* は毎回同じ答えを返す。
それでは分岐を作った意味が無い。コストを動かす案は次のとおりで、**推しは 1 つ目**。

1. **タワーの射程に入っている辺はコストが上がる**（敵は守りの薄い枝を通ろうとする）
   - グリッド設置と直結する。どこに置くかで敵の流れが変わり、置き方が戦術になる
   - プレイヤーから見て「なぜそっちに行ったか」が説明でき、理不尽にならない
2. 戦士が塞いでいる辺のコストが上がる（迂回させて足止めする）
3. 敵の種類で重みを変える（高速敵は最短、装甲敵は守りの厚い枝でも突っ込む）

1 だけでも成立し、2・3 は同じ「辺の重み」を触るだけなので後から足せる。

**既存コードへの波及**

グラフ化は `PathFollow3D` 前提の箇所に触るので、影響範囲を先に洗っておく。

- `Enemy`: `PathFollow3D` の `progress` を進める形 → 辺を渡り歩く形に置き換え
- `Tower._find_target`: 「ゴールに一番近い敵」を `progress_ratio` で測っている。
  グラフでは **A\* が返す「クリスタルまでの残りコスト」がそのまま使える**（小さいほど優先）
- `RoadVisual`: 辺ごとにリボンを張る。節での重なりだけ処理が要る
- `Terrain` / `PropScatter`: どちらも「道の中心線を点にした配列」しか見ていないので、
  全部の辺から点を集めるように変えるだけで済む

### 16.3 構造で変わるところ

**状態を「周回」と「ステージ」に割る**

今の `GameState` は 1 ステージぶんの状態しか持っていない（gold / lives / wave）。周回では
「ステージをまたいで残るもの」と「ステージごとに作り直すもの」が混ざるので、ここを割る。

- 周回に属する: 現在ステージ・ゴールド・強化レベル
- ステージに属する: ライフ・ウェーブ・道・設置したタワー

**ステージをデータにする**

今は `Curve3D` も設置マス 10 個も `main.tscn` に直置き。これを `StageData (Resource)` に移し、
Level が起動時に自分を組み立てる形にする。データ駆動の既存方針（§9）の延長。

タワー配置のリセットは Level を作り直すだけで済む（`GameState` は Autoload なので生き残る）。
リスタートで使っている `reload_current_scene` の仕組みがそのまま使える。

**v1.1 の作りがそのまま効く**

地形は `Path3D` と `BuildSpots` を `_ready` で読んで「道と設置マスの周りを平らに均す」ので、
道が変われば均し方も自動で付いてくる。道のリボン・小物のばら撒き（道を避ける判定）・
クリスタルの接地も同じ。**ステージごとに見た目を作り込む必要は無い。**

**タワーのティアと武器強化は同じ仕組み**

別々に作ると二重実装になる。`TowerData` と戦士の武器を同じ強化ルールで扱う。
Desktop の 5 段モデル（`tower_basic_1 → cannon_2 → heavy_3 → siege_4 → apex_5`、
元の .blend は `C:\Users\Itsuk\Desktop\新しいフォルダー`）はタワー側の段階として乗る。
すべてベーシックタワーの上位砲塔なので、別種のタワーではなく段階として入れる。
土台は 1 種類のままにして砲塔だけ差し替えれば、書き出すのは Turret だけで済む。
書き出し: `blender -b <blend> --python tools/export_tower_models.py -- assets/models <接頭辞> <出力名>`

### 16.4 順番

方針は v1.1 と同じで「構造を変える作業を、抱えている中身が少ないうちに済ませる」。

| # | やること | 状態 |
| --- | --- | --- |
| 1 | 演出（ヒットフラッシュ / 効果音 / 簡単なパーティクル） | ✅ 済 |
| 2 | 周回の器 ＋ ステージのデータ化（道をグラフで持つ／分岐はまだ使わない） | ✅ 済 |
| 3 | 分岐と A\*（敵の枝選択）＋ タワーのグリッド設置 | ✅ 済 |
| 4 | 戦士 1 種（雇用・スポーン・道に沿って前進・足止め） | ✅ 済 |
| 5 | 役職 3 種 ＋ 強化システム（タワーのティア / 武器） | ✅ 済 |
| 6 | バランスの取り直し（`balance_sim` を周回対応に） | ✅ 済 |
| 7 | 残り（敵の追加種・無限モード・**効果音の差し替え**・リッチ VFX / BGM） | 効果音まで ✅ |

**1 が先の理由** — 他のどれとも噛み合わない独立した作業で、いつやっても手戻りが無い。
先に入れておくと、以降の試遊で「当たったのか外れたのか」がひと目で分かるようになる。

1 で入れたもの: 被弾フラッシュ、撃破・着弾・砲口・設置のパーティクル
（`scripts/burst.gd`、GL Compatibility で確実に動く CPUParticles）、効果音 9 種
（初期版は `tools/make_sfx.py` で合成、現在は CC0 素材へ差し替え済み）、
ライフが減ったときのクリスタルの脈打ち。
発射音は `TowerData.shoot_sfx` に持たせたので、タワーが増えても `.tres` だけで済む。

効果音は Kenney と rubberduck の CC0 素材へ差し替え済み。連射される発射・命中音は
短く丸い音を選び、勝敗は同系統のスチール音色で統一した。`assets/audio/` の WAV 名を
維持したため `Sfx.LIBRARY` のパスは変えていない。出典は `assets/audio/SOURCES.md` を参照。

**2 でグラフの器まで作る理由** — ステージをデータにするとき、道を `Curve3D` 1 本で持つと
3 で必ず作り直しになる。最初からグラフとして持ち、ステージ 1 は「分岐 0 本のグラフ」
として扱えば、3 は**データを増やすだけ**で済む。器を先に正しい形にしておく。

2 で入れたもの:

- `RouteData` … 節と辺のグラフ。実データはまだ全部「一列の鎖」だが、
  `has_branch()` の判定だけ先に持たせて、枝を入れたときに気づけるようにした
- `StageData` / `CampaignData` … 道・設置マス・ウェーブ・報酬をステージごとに持つ。
  周回の並びは `resources/campaign.tres`
- `Level` … `StageData` から道・設置マス・拠点の位置を組み立てる。
  **組み立ては `_ready` ではなく `_enter_tree`**。`_ready` は子が先に走るので、
  `Terrain` と `RoadVisual`（どちらも `_ready` で `Path3D` と `BuildSpots` を読む）に
  間に合わない
- `GameState` … 周回に属する状態（ステージ番号・ゴールド）と、ステージごとに戻す状態
  （ライフ・ウェーブ）を `reset_run()` / `advance_stage()` に分けた。
  ステージ並びの読み込みは遅延させている。Autoload の `_ready` とメインシーンの
  `_enter_tree` のどちらが先かに依存させないため（実際にここで一度踏んだ）
- `IntervalScreen` … 勝敗画面と同じ「ツリーを止めて Control を出す」型。強化 UI は 5 で入る
- ステージ 3 つ（`tools/make_stages.py` が座標を検算してから `.tres` を書き出す）

**ステージ 1 は v1.0 と同じ道**にしてある。既存のバランス基準をそのまま生かすため。
確認: タワー 3 本 → 波 5 で敗北（基準どおり）、10 本 → ステージクリア（ライフ 3 残し）。

**3 を 4 より前に置く理由** — 戦士も同じ道グラフを辿るので、辺の渡り方が決まる前に
戦士を作ると作り直しになる。3 はバランスの数値も必ず取り直しになる作業なので、
種類が少ない今のうちに済ませたい（今なら タワー 2 種 × 敵 2 種ぶん）。

3 の前半で入れたもの:

- `RouteGraph` … RouteData を走れる形にしたもの。**節に着くたびに A\* で経路を出し、
  次の辺を選ぶ**。見積もりはゴールまでの直線距離で、辺のコストは「長さ ＋ 0 以上の追加」
  なので直線距離を下回らない＝許容的（最短を取り逃がさない）。
  節が数十個なので開集合は配列の線形探索で足り、優先度付きキューは持ち込んでいない
- **辺のコストはタワーで動く** … タワーの射程に入っている長さぶんコストが上がる
  (`THREAT_WEIGHT`)。コストが固定だと A\* は毎回同じ答えを返し、分岐を作った意味が無くなる。
  コストが変わったら version を進めてキャッシュを捨てる
- `Enemy` … `PathFollow3D` をやめて自前で辺を渡り歩く。1 フレームで節を 2 つ以上
  またぐこともあるので、乗り換えは while で回す
- タワーのターゲット選択 … 「進行度が最大の敵」では分岐があると順位が付かないので、
  **A\* が選んだ経路の残り距離が最小の敵**に変えた
- `RoadVisual` … 辺ごとにリボンを張る。辺の両端を道幅ぶん伸ばして直角の外側の欠けを埋め、
  辺ごとに極小の高さ差を付けて重なりのちらつきを避けている
- ステージ 3 を分かれ道にした。**2 本の枝は同じ長さ (16)**。長さで差が付いていると
  A\* が常に同じほうを選んでしまうので、守り方だけで選択が決まるようにした

**枝の選択は抽選にした。** 最初は A\* が返す最安の枝をそのまま使っていたが、
それだと**全部の敵が同じ道を通ってしまう**（全マスにタワーを建てても一切分岐しなかった）。
ゴールまでのコストが安い枝ほど選ばれやすい抽選に変え、重みは
`(最安 / その枝) ^ BRANCH_SHARPNESS`。比で見るので道の長さに依存せず、
コストが同じなら五分五分になる。乱数の種は固定してあるので、同じ配置なら同じ流れになり
バランス検証を繰り返しても結果がぶれない。

| タワーの状態 | コスト A | コスト B | 枝 A へ | 枝 B へ |
| --- | --- | --- | --- | --- |
| なにも建てない | 25.0 | 25.0 | 52% | 48% |
| 枝 A だけ守る | 40.0 | 26.5 | 28% | 72% |
| 全部のマスに建てる | 110.0 | 109.0 | 46% | 54% |

バランスの回帰も確認（タワー 3 本 → 波 5 で敗北。`PathFollow3D` のときと同じ）。
偏りを強めたい・弱めたいときは `BRANCH_SHARPNESS` の 1 か所だけを触ればよい。

3 の後半で入れたもの:

- `BuildGrid` … 置けるマスを**地形と道から機械的に割り出す**。高台の内側か、拠点に
  近すぎないか、そして**道沿いの 1 マスぶんか**。ステージ 1 で 33 マス。道を描くだけで
  マスが付いてくるので、ステージを増やしても座標を用意しなくてよい
  （`StageData.build_spots` は廃止）
- 置けるのは**道沿い 1 マス**だけ。高台じゅうに置けるようにすると射程の届かない奥にも
  建てられてしまい、盤面が広いだけで選ぶ楽しさにならない。上限に「マスの半分」を足して
  いるのは、道がマスの線に重なっているかどうかで帯の幅が変わらないようにするため
- **マスに対応するノードは作らない。** 100 マス近くを Area3D にしても得られるものが無い。
  クリック位置は「カメラのレイと高台の上面 (y=0) の交点」から割り出し、割り算でマスを求める
- マスは**道に近い順**に並べてある。検証ツールが上から順に建てるだけで、
  射程が道に届くまともな配置になる
- `BuildGridView` … MultiMesh で盤面をまとめて描く。マスが道沿いに絞られていて
  画面の邪魔にならないので、**盤面は常に出しておく**（探さずに済む）。
  タワー選択に連動するのはカーソルの光だけ。カーソルは草の上で緑が沈むので白寄りの明るい色
- タワーは**マスごとの地面の高さに乗せる**。起伏を均す必要がなくなったので、
  地形を平らにするのは道の周りだけになった。足元には石の土台を敷いて据わりを出す
- 建てた場所の岩や茂みは**どける**。どこにでも建つようになった以上、小物のほうを
  避けておくことができない（避けると高台から小物が消える）

**バランスは動いた。** グリッドだと手で置いていたマスより道に近づけられるため、
全体に易しくなっている。§16.4-6 で取り直す前提の変化なので、ここでは数値を触っていない。

| 10 本（減速砲 1/3） | 勝利・ライフ 4〜12 残し | 勝利・ライフ 12 残し |

4 で入れたもの:

- `WarriorData` / `Warrior` / `WarriorManager` … ゴールドで雇い、拠点から出て道を遡る。
  **経路探索は要らない。** 道グラフを「ゴールから遠ざかる向き」に辿るだけ
  (`RouteGraph.next_node_away`)。行き先を選ぶ理由があるのは敵のほうで、
  戦士は前へ出ていくだけなので敵の A\* を使い回していない
- **1 人が足止めできる敵は 1 体。** 手が空いている戦士がいなければ敵は素通りする。
  この規則だと「何人出したか」がそのまま止められる数になり、画面を見れば何が起きているか分かる
- 倒れた戦士は戻ってこない（**消耗品**）。タワーと同じ財布から出すので、
  「守りに置くか、前に出すか」の選択になる
- 同時に出せるのは 8 人まで。ゴールドだけで抑えると道を塞ぐ壁になってしまう
- 同時に雇うと全員が同じ位置に重なるので、道の中心から左右へ散らして横並びに見せている

10 秒 戦士 3 人 / 敵 4 体（足止め 3）/ ライフ 20   … 3 体を掴んでいる
15 秒 戦士 3 人 / 敵 0 体（足止め 0）/ ライフ 20   … 全部倒し、誰も通していない

**バランスについて** — §13 の基準（タワー 3 本 → 波 5 で敗北 など）は「1 ステージぶんの
基準」として残るが、戦士が入った時点で成立しなくなる。周回全体の基準は 6 で立て直す。
それまでは既存の基準を壊さない範囲（＝ `.tres` の数値を触らない）で進める。

なお **道が長くなっても難しくはならない**。むしろタワーが撃てる時間が増えるぶん易しくなる。
ステージ 1 → 3 で道は 40 → 45 → 67 と伸びているので、難度はウェーブ側で作ること。
ステージ 2・3 のウェーブはまだ仮（後半の 4 波を流用しているだけ）で、6 で組み直す。

5 の前半（役職 3 種）で入れたもの:

- **役職の違いは `block_capacity` と `attack_range` の 2 つで作る。** HP とダメージの
  大小だけで分けると「強い戦士／弱い戦士」にしかならず、揃える理由が生まれない。
  仕事のほうを分けた

| 役職 | block_capacity | attack_range | 費用 | HP | 仕事 |
| --- | --- | --- | --- | --- | --- |
| 盾兵 | 2 | 1.3 | 60 | 100 | 2 体まとめて止める。倒す力はほぼ無い（2 dps） |
| 衛兵 | 1 | 1.1 | 40 | 40 | 1 体を止めて、そのまま倒す（6 dps） |
| 弓兵 | 0 | 4.5 | 50 | 24 | 止めない。前列の後ろから撃つ（4.5 dps） |

- **敵 1 体を掴めるのは 1 人だけ**（4 から変わらず）。盾兵が 2 体を抱えている間は
  衛兵がその 2 体に手を出せないので、誰が誰を持つかが操作なしで分かれる。
  掴まない弓兵はこの取り合いに参加しないので、前列が抱えている敵を撃てる
- **すれ違いざまの反撃を敵に足した**（`Enemy._strike_passing`）。これが無いと弓兵は
  一切傷つかず、「弓兵だけ並べる」が最適解になってしまう。足は止めない
  ——止めると、足止めしないはずの役職が足止め役になってしまう
- 見下ろしの引きでは顔も装備の細部も読めないので、**役職はシルエットで分ける**。
  盾は体より広い板、剣は斜め、弓は体の輪郭の外へ出した縦棒。
  弓を体に重ねて置いたときは頭の上に少し覗くだけで形にならなかった
- 弓兵の体色は最初 緑にしていたが、**スライムと見分けが付かない**ので紫にした
- ボタンは 2 行に分けた（上＝戦士 3 種、下＝タワー 2 種）。1 行だと 5 個で横幅を超える

確認（役職 3 種を 1 人ずつ・タワーなし・波を 2 つ重ねる。`-- warrior`）:

```
 5 秒 敵 3 体（足止め 1）/ ライフ 20 / 盾兵 0体 衛兵 1体 弓兵 1体
10 秒 敵 2 体（足止め 2）/ ライフ 20 / 盾兵 2体 衛兵 0体 弓兵 1体
15 秒 敵 0 体（足止め 0）/ ライフ 20 / 盾兵 0体 衛兵 0体 弓兵 0体
```

10 秒の行が役職の切り分けそのもの。**足止め 2 = 盾兵 1 人が抱えた 2 体**で、
衛兵は掴む相手が居なくなって 0 体、弓兵は掴まないまま 1 体を撃っている。

弓兵だけを並べたとき（`-- archer`）は 20 秒で 3 人 → 2 人。すれ違いざまの反撃が
効いていて、前列を用意しない構成は崩れる。

**残りは強化システム**（タワーのティア / 武器）。Desktop の 5 段モデル

ステージ移行でタワー配置はリセットされるので、強化は**置いたタワー 1 本ではなく
タワーの種類そのもの**に掛ける（インターバルで買う → 以降そのティアで建つ）。

5 の後半（強化システム）で入れたもの:

- **強化は置いたタワー 1 本ではなく、タワーの種類そのものに掛かる。**

- Desktop の 5 段モデルをここで消化した。`tools/export_tower_models.py` で `.glb` にし、
  `tools/make_tower_tiers.py` が `.tres` と `.tscn` を**検算してから**書き出す

| 段 | 名前 | 設置 | ダメージ | 射程 | 次段へ |

| 1 | アロータワー | 50 | 4 | 6.0 | 150 |

- **設置費用も段ごとに上げてある。** 上げないと強化は一方的に得になるだけで、
  「1 ステージに何本置けるか」の判断が消えてしまう
- 戦士の武器は**役職ごとではなく全体に 1 本**（Lv 0〜3、1 段 +30%）。
  一律 +N ではなく割合なのは、素のダメージが小さい盾兵（2）だけが不釣り合いに強くなり、
  役職の切り分けが崩れるため
- 強化を買う場所は `IntervalScreen`（2 で器だけ作ってあったところ）。
  **鎖を持たない種類は行に出さない**。フロストタワーに「最大」と出しても意味が無く、
  買えるものを探す手間が増えるだけになる
- タワーの当たり判定・足元の石・カメラの寄りは、**モデルの実物を測って**決めるようにした
  （`Tower._measure_visual`）。段ごとに数値を書くとモデルを差し替えるたびに書き直しになる

**土台は砲身を数えず、土台部分だけで測る。** 最初は全体の AABB で測っていたが、
上位ティアは砲身が 1.3 m 伸びるので石の土台が隣のマスまで広がり、道まで覆ってしまった。
砲身は旋回するので「その場を占めている広さ」を表さない。

- `balance_sim` を**周回対応**にした。`--campaign` でステージ 1 から最後まで通しで走り、

  `--stage` / `--gold` で途中のステージだけを詰められる。`--warriors` で戦士も雇う
- `WaveEntry.hp_scale` … **波ごとの敵の硬さ**。ここまで難度は数と間隔でしか作れず、
  後半は画面を埋め尽くす物量にしかならなかった
- `tools/make_waves.py` … 26 波を 1 つの表から書き出す。**書き出す前に検算する**

**測って分かったこと（どれも実測で潰した）:**

1. **盤面を埋められると何をしても勝ててしまった。** 全 34 マスに最上位タワーを建てると
   ステージ 3 でライフを 1 も失わない。原因は敵の硬さではなく**収入**で、
   グリッド設置でマスが 10 → 33 に増えたのに費用が v1.0 のままだったため。
   費用をおおむね 4 倍にして、1 ステージで建てられるのが 15 本前後になるようにした
2. **数で難度を作ると収入も一緒に増える。** ステージ 2・3 は敵の数をステージ 1 と
   ほぼ同じ（205 / 207 / 213 体）に据え置き、**硬さ (hp_scale) だけで上げる**ようにした。
   1 ステージの収入がほぼ据え置きになるので、「安いタワーを並べるか、高いタワーを少なく置くか」
   の選択が最後まで生きる
3. **ステージの 1 波目は必ず軽く始める。** 設置はステージごとにリセットされるので、
   1 波目は盤面がほぼ空のまま受けることになる。前ステージの終盤の重さで始めたら
   建て直す前に押し切られた（波 3 で敗北）
4. **序盤のタワー 1 本は途中の 1 本よりずっと重い。** 開始直後に戦士を雇って
   タワーが 1 本減っただけで、そのタワーが稼ぐはずだったゴールドまで失って
   ライフ 17 残しの勝利が敗北に変わった。開始ゴールドはこの感度を見ながら 1100 に決めた
5. **足止めされた敵にタワーが張り付いていた。** 足止め中の敵はその場に留まるので、
   「ゴールドに近い順」で撃つと全部のタワーがその 1 体を狙い、後ろの群れが素通りしていた。
   足止め中の敵は後回しにする（`Tower.BLOCKED_PENALTY`）ように変えた
6. **戦士が湧き口まで出て行って溶けていた。** タワーの傘の外で戦っても意味が無いので、
   `WarriorData.advance_limit` で拠点から 6〜11 m までしか前に出ないようにした
   （盾兵が一番前、弓兵が一番後ろ）

**戦士はまだ差し引きマイナス。** 5 と 6 で「雇うと明確に弱くなる」までは直したが、
周回で 4 人抱えると最終波で 1 歩届かない（雇わなければクリアできる）。
同じゴールドならタワーのほうが強い、というのが今の数値。ここは 7 で詰める。

| 何 | どこ |
| --- | --- |
| 波の中身（数・間隔・硬さ） | `tools/make_waves.py` |
| ステージの道・報酬・波の割り当て | `tools/make_stages.py` |
| タワーのティア（費用・強化費用・性能） | `tools/make_tower_tiers.py` |
| 開始ゴールド・武器強化の費用 | `scripts/game_state.gd` |
| 戦士 | `resources/warriors/*.tres` |

7 の前半（戦士の立て直し）で入れたもの:

6 で「戦士は差し引きマイナス」と分かったので、原因を 3 つに分けて潰した。

1. **戦士が仕事をしていなかった**（前に出る距離が足りない）… `advance_limit` を
   拠点から 6〜11 m → **13〜20 m**（盾兵が一番前、弓兵が一番後ろ）。
   6 では「タワーの傘の外で溶ける」と考えて手前に置いたが、盤面は道全体に広がるので
   傘は道の中ほどまで届いている。手前すぎると**そこまで漏れてきた敵しか相手にできず**、
   ほとんどの時間ただ立っていた
2. **敵が硬くなると戦士だけ置いていかれる**… `WarriorData.damage_percent` を足して、
   ダメージを「固定ぶん ＋ **相手の最大 HP の割合ぶん**」にした（衛兵 6% / 弓兵 4% / 盾兵 2%）。
   硬い敵ほど一撃も重くなるので、「硬い 1 体を捕まえて削る」仕事が最後まで成立する
3. **足止めした敵を誰も撃たなかった**… タワーが足止め中の敵を完全に無視していたのを、
   「8 m ぶん後ろにいる扱い」に緩めた（`Tower.BLOCKED_PENALTY`）。
   あわせて**足止め中の敵は受けるダメージ +50%**（`Enemy.HELD_DAMAGE_BONUS`）。
   戦士の仕事を「自分で倒す」から**タワーに倒させる**に寄せている

ここまでで「雇っても雇わなくてもほぼ同じ」（差し引きゼロ）になった。
残っていたのは **同じゴールドを注ぐならタワーのほうが確実**という点で、
埋めるには「戦士にしかできない仕事」が要る。そこで 4 つ目を足した。

4. **道に居座ると、その道は敵に嫌われる**（`WarriorData.threat_length`）。
   タワーは建てた場所から動かないが、戦士は**道の上に立てる**。立っている辺の
   経路コストを上げるので、分かれ道の片方に置けば流れをもう一方へ寄せられる。
   `RouteGraph` には引く側 (`remove_threat`) を足した——戦士は動くし倒れるので、
   タワーと違って戻す処理が要る

確認（ステージ 3 の分かれ道。`-- stage3 steer`）:

```
戦士なし          コスト A=25.0 B=25.0 → 枝A 52% / 枝B 48%
盾兵 3 人を配置   コスト A=32.0 B=43.0 → 枝A 64% / 枝B 36%
戦士が倒れたあと  コスト A=25.0 B=25.0 → 枝A 48% / 枝B 52%
```

置けば寄り、倒れれば戻る（**上げたコストが残らない**ことまで確認している）。

周回での結果:

| 走らせ方 | 結果 |
| --- | --- |
| 戦士なし | 勝利・ライフ 13 残し |
| 戦士 3 人 | 勝利・**ライフ 15 残し** |
| 戦士 6 人 | 最終波で敗北（タワーが 2 本減る） |

**数人までは得、増やしすぎると損**という形になった。戦士は盤面の代わりではなく
補助、という位置づけが数字にも出ている。ライフの差は乱数のぶれ（±5）と同じくらいなので、
「明確に得」と言い切れるのは**流れを寄せられること**のほう。

**フロストタワーは後半になるほど混ぜる価値が薄い。** 強化の鎖を持たないので、
段が上がったアロータワーの系列に対して見劣りする（実測: 周回で減速砲を混ぜないほうが
ステージ 3 のライフが多く残った）。費用を 220 → 170 に下げて折り合いを付けたが、
本筋は**減速側にも段を用意すること**。モデルが要るので保留にしてある。

7 の後半（敵の追加種・無限モード）で入れたもの:

**装甲 (`EnemyData.armor`)** … 1 発ごとに引く数値。**HP を増やすのとは効き方が違う。**
HP は「弱い弾をたくさん」でも「強い弾を少し」でも同じだけ効くが、装甲は 1 発ごとに
引かれるので**弱い弾を連射するほど損**になる。タワーの段を上げる理由がこれで増える。

| 敵 | HP | 装甲 | 1 発で通る量（硬さ ×3 の波） |
| --- | --- | --- | --- |
| スライム | 25 | 0 | アロー 4 / ヘビー 11 / エイペックス 22 |
| はやいスライム | 16 | 0 | 同上 |
| 装甲スライム | 40 | 2 | アロー **1** / ヘビー 8 / エイペックス 19 |
| ボススライム | 320 | 4 | アロー **1** / ヘビー 4 / エイペックス 15 |

**ボス**はステージ 2 の最終波と、ステージ 3 の波 8・10 に 1 体ずつ。
体が 1.9 倍あり、抜けられるとライフを 5 持っていく。

見た目は**腰まわりの装甲帯**で見分ける。最初は体をすっぽり覆う殻にしたが、
元の体色が見えなくなって敵種が分からなくなり、上に乗せると帽子に見えた。

**無限モード** … 全ステージを守り切ると勝利画面に「無限モードへ」が出る。
**ゴールドと強化を持ったまま**ステージ 1 から周り直し、1 周ごとに敵の硬さへ
`ENDLESS_STEP`（+35%）が乗る。

波を無限に用意することはできないし、用意しても後半は数の暴力にしかならない。
**硬さの倍率 1 つで伸ばす**なら、獲得ゴールドは増えないので稼ぎも自然に締まる
（1 ゴールドあたりの HP が周回ごとに重くなる）。
負けたときの表示が「何周目のどこで力尽きたか」＝そのままスコアになる。

確認（`-- endless`）:

```
勝利画面 表示=true / 無限モードのボタン=true
押した後      周回=1 硬さ×1.00 ステージ 1
1 周まわした後 周回=2 硬さ×1.35 ステージ 1
```

**バランスは取り直した。** 装甲持ちが入ったぶんステージ 2・3 が重くなったので、
ステージ 3 の硬さを下げて釣り合いを戻している。

| ステージ | 残ったライフ（`--campaign` を 2 回） |
| --- | --- |
| 1 | 20 / 20 |
| 2 | 12 / 13 |
| 3 | 14 / 8（クリア） |

ステージごとに確実に減っていく形になった（6 の時点ではステージ 2 が 20/20 で素通りだった）。

無限モードの通し（`--campaign --endless`）:

```
1 周目  ステージ1 20 → ステージ2 11 → ステージ3  9（クリア）
2 周目  ステージ1 20 → ステージ2 20 → ステージ3 14（クリア）
3 周目  ステージ1 20 → ステージ2 20 → ステージ3 15（クリア）
4 周目  ステージ1 20 → ステージ2 20 → ステージ3 最終波で敗北（硬さ ×2.05）
```

**2〜3 周目が 1 周目より楽なのは意図どおり。** 1 周目は強化を買いながら走るが、
2 周目に入るころには段が上がり切っていて、+35% を追い越している。
強化が打ち止めになると増分だけが残るので、そこから 1〜2 周で終わる。
「強化を伸ばしきる時間」と「硬さの増分」の競争になっている。

伸ばしたい／縮めたいときは `GameState.ENDLESS_STEP` の 1 か所だけを触ればよい。

### 16.5 開発者パネル（製品版には出ない）

試遊を速くするための道具。`scripts/dev_panel.gd`、**F3** で出し入れする。

| ボタン | すること |
| --- | --- |
| ゴールド +1000 | 支払いを通さずに増やす |
| 敵を全滅 | 今出ている敵を倒す（倒した扱いなのでゴールドも入る） |
| ステージクリア | 守り切ったことにしてインターバルへ飛ぶ |
| 無敵 | ライフを減らさない |
| 早送り | ×1 / ×2 / ×4 |

**リリース書き出しでは丸ごと消える。** `OS.is_debug_build()` が false のとき
`_ready` で自分を `queue_free()` する。「隠す」ではなく**ツリーから消す**のは、
隠しただけだと入力やショートカットが生きたままになり、何かの拍子に製品版で
効いてしまうため。既定でも隠してあるのは、撮影ハーネスに毎回写り込まないようにするため。

`export_presets.cfg` の `exclude_filter` に `tools/*` を入れて、
検証用スクリプト（`balance_sim` / `vis_preview` / `headless_check`）も
製品版のパックから外した。Web 書き出しが通ることは確認済み。

ここのボタンは**ゲームの規則を曲げる**もので、バランスの測定には使わない
（測定は `tools/balance_sim.gd`）。
